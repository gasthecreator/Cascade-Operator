# Phase 6.6 (slice 3): `spec.mesh` reconciler dispatch, live-verified

**Date:** 2026-08-31
**Author:** Claude (solo — Cursor unavailable)
**Type:** refactor (existing `queryBuilder()`/`mitigator()` gain a required
`policy` parameter and dispatch on `policy.Spec.Mesh`; no change to the
default Istio behavior when `spec.mesh` is unset)

## What
- `CascadePolicyReconciler.queryBuilder`/`mitigator` (`cascadepolicy_controller.go`)
  now take `*cascadev1alpha1.CascadePolicy` and dispatch:
  `policy.Spec.Mesh == MeshLinkerd` → `internal/mesh/linkerd`'s
  `QueryBuilder{}`/`NewMitigator(r.Client)`; anything else (including the
  unset zero value, `spec.mesh`'s own `+kubebuilder:default=Istio`) →
  `internal/mesh/istio`'s implementations, exactly as before. `r.QueryBuilder`/
  `r.Mitigator` still take priority when explicitly set (every existing test
  that injects a `fakeQuerier` alongside a specific mesh's query shapes
  relies on this override remaining first).
- Every call site updated to pass `policy` — `evalLatencyError`/
  `evalRetryStorm` (previously missing a `policy` parameter entirely;
  `evalFanOut` already had one) plus every `r.mitigator()` call across
  `mitigate.go`, `retry_mitigate.go`, `fanout_mitigate.go`, `restore.go`,
  `retry_restore.go`, `fanout_restore.go` — `policy` was already in scope
  at every one of these call sites, so this is a mechanical, low-risk
  change (confirmed: the full existing test suite passes unmodified,
  real evidence this preserved exact behavior for the default Istio path).
- `cascadepolicy_controller_test.go`'s shared `fakeQuerier.Query` extended
  to recognize Linkerd's own query shapes
  (`route_actual_request_total` for retry storm, `direction="inbound"`
  for fan-out — Linkerd has no `reporter=` label at all, unlike Istio)
  ahead of the existing Istio-specific substring checks, so any future
  reconcile-level test can drive a Linkerd-mode policy through this same
  fake without a second querier type.
- `internal/controller/mesh_dispatch_test.go` (new): reconciler-level
  tests proving the dispatch itself, not just that `internal/mesh/linkerd`
  works in isolation (already covered by that package's own tests) —
  a Linkerd-mode policy trips a Service's failure-accrual annotations and
  never touches a DestinationRule; an explicitly-unset `spec.mesh` still
  defaults to Istio's DestinationRule path; a Linkerd-mode retry-storm
  policy runs a full trip-then-restore-to-completion cycle through
  `Reconcile` itself (six ticks), ending with the ServiceProfile's
  `retryBudget` back at its true original and both operator annotations
  gone.
- `istio_patch_test.go`'s shared `patchTestScheme` extended to also
  register `corev1`/`internal/mesh/linkerd/serviceprofile/v1alpha2` —
  harmless to the Istio-only tests already using it, and now every
  existing fake-client test in this package can build a Linkerd-mode
  fixture without a second scheme helper.

## Why
PLAN.md §5 Phase 6.6's last real gap before integration coverage: the
prior two slices built `internal/mesh/linkerd`'s `QueryBuilder`/`Mitigator`
and live-verified each in isolation, but `queryBuilder()`/`mitigator()`
still always returned the Istio implementation regardless of
`policy.Spec.Mesh` — a `CascadePolicy` author setting `mesh: Linkerd` had
no way to actually get Linkerd's detection/mitigation, only Istio's
(silently, since nothing rejected the field value — the CRD's OpenAPI enum
already accepted `Linkerd`, it just had no effect on which code ran).

## Live verification (real cluster, real `Reconcile()` — not only the new fake-client tests)
Built a small throwaway program (`cmd/_live_verify_tmp`, deleted after
use — not committed) that:
1. Created a real `ServiceProfile` for `inventory-service` on the dev
   cluster's `linkerd-demo` namespace, seeded with
   `{retryRatio: 1.0, minRetriesPerSecond: 10, ttl: 10s}`.
2. Created a real `CascadePolicy` with `spec.mesh: Linkerd`,
   `dependsOn: [inventory-service...]`, `mode: Mitigate`.
3. Ran the actual, unmodified `CascadePolicyReconciler.Reconcile` — the
   exact method the deployed operator binary calls — with a fake
   `metrics.Querier` that trips retry storm specifically (recognizing
   `route_actual_request_total`, Linkerd's own retry-storm-ratio query,
   and returning a healthy value for every other query shape).

Result: `policy.Status.Phase = Tripped`, `LastSignature = RetryStorm`, and
the real `ServiceProfile`'s `retryBudget` came back as
`{RetryRatio:0 MinRetriesPerSecond:0 TTL:10s}` with both operator
annotations present (`managed-by=cascade-operator`,
`original-retry-budget={"retryRatio":1,"minRetriesPerSecond":10,"ttl":"10s"}`)
— proving the dispatch wiring works end-to-end against a real API server
through the real `Reconcile` path, not merely through direct `Mitigator`
calls (the previous slice's own live check) or the fake-client unit tests
added in this slice.

# Phase 6.6 follow-up: wire Linkerd into CI's integration job

**Date:** 2026-09-01
**Author:** Claude (solo — Cursor unavailable)
**Type:** CI (workflow-only change; no Go source, no new tests)

## What
`.github/workflows/integration.yml`: adds a `make linkerd-install` step
right after the existing `make istio-install` one, sets
`LINKERD_VERSION: "edge-26.6.3"` (matching the Makefile's own pin),
renames the job from `Kind + Istio 1.30.4` to
`Kind + Istio 1.30.4 + Linkerd edge-26.6.3`, and bumps `timeout-minutes`
from 30 to 40 to give a second mesh control plane real install-time
headroom. No branch protection rule references the old job name (checked
via `gh api repos/.../branches/main/protection` — 404, unprotected), so
the rename carries no required-status-check risk.

## Why
Every prior Phase 6.6 slice's own worklog flagged this exact gap: the
`test/integration/linkerd_*.go` tests already existed and passed against
the dev cluster, but this workflow only ever installed Istio, so
`verifyLinkerdClusterReady` made them skip in CI rather than actually
run. This closes that gap — the last explicitly-deferred item from Phase
6.6's five slices.

## How
Ordering: create cluster → install Istio → install Linkerd → install
CascadePolicy CRDs → run tests. Both meshes install onto the same fresh
Kind cluster in disjoint namespaces (Istio's demo topology in `default`,
Linkerd's in `linkerd-demo`) — the identical one-cluster-two-meshes shape
already used on the dev machine since the `QueryBuilder` slice's own
spike, where the two were confirmed not to conflict as long as injected
workloads stay in separate namespaces.

This is also the first real exercise of `hack/install-linkerd.sh`'s
**`install` code path** specifically: every live run of that script this
project has done so far (across the `Mitigator`, reconciler-dispatch, and
integration-test slices) ran against the same *persistent* dev cluster,
which already had a Linkerd control plane from the very first spike — so
those runs all took the script's `upgrade` branch (the real bug that
branch exists to work around). CI's `kind create cluster` step always
starts genuinely fresh, so this workflow run is what actually confirms
the plain `install` path, not just the `upgrade` one, since neither this
project's dev machine nor this workflow had exercised it end-to-end
before now.

## A real, honestly-flagged risk going in, not glossed over
This project's own worklogs (`QueryBuilder`/`Mitigator`/install-script
slices) document repeated, genuine resource exhaustion on the dev
machine's Kind node — running Istio's full stack plus Linkerd's full
stack (control plane + linkerd-viz: `metrics-api`/`tap`/`tap-injector`/
`web`, not only the `prometheus` this project's own detection actually
needs) simultaneously pushed even `kube-apiserver`/`kube-scheduler` into
restart loops on a 4-CPU/5GB-limited container. GitHub's standard
`ubuntu-latest` runners have less headroom (2 vCPU / ~7GB total for the
whole runner, not just the Kind node), so this same combination could be
tight there too. This was not preemptively worked around (e.g., trimming
`linkerd viz install` to only the components this project's own
`QueryBuilder` needs) — that would be scope creep beyond "wire up the
existing script," and the honest, verify-don't-assume approach is to
actually run it in CI and fix whatever real failure shows up, not guess
at one that might not occur.

## The CI run's own first failure — a real bug, not the flagged resource risk
The first run of this workflow failed in ~3.5 minutes — too fast to be
the resource-exhaustion risk flagged above (that would show up as a
`rollout status` timeout well into the run, not an early test failure).
The actual failure:
```
=== RUN   TestLinkerdFanOutDetectOnlyNeverPatchesTheService
    linkerd_fanout_test.go:44: kubectl apply -f .../demo/k8s-linkerd: exit status 1
        namespace/linkerd-demo created
        deployment.apps/payments-service created
        service/payments-service created
        Error from server (NotFound): error when creating ".../demo/k8s-linkerd/cascadepolicy.yaml": namespaces "linkerd-demo" not found
        Error from server (NotFound): error when creating ".../demo/k8s-linkerd/checkout.yaml": namespaces "linkerd-demo" not found
        ...
```
`applyLinkerdDemoFixtures` (from the integration-tests slice) ran a single
`kubectl apply -f demo/k8s-linkerd` over the whole directory — including
`namespace.yaml` itself alongside the namespaced objects that depend on
it. `kubectl apply -f <dir>` does not guarantee the apiserver has made a
just-created Namespace visible before processing the next object in the
same batch that references it; this is a genuine race, not a hypothetical
one, and — critically — it was invisible in every one of this project's
own prior local live-verification passes purely because `linkerd-demo`
had existed continuously on the persistent dev cluster since Phase 6.6's
very first spike, never actually deleted between sessions. CI's `kind
create cluster` step starts genuinely fresh every run, which is exactly
what exposed it — the reason this project runs live checks against a real
cluster in the first place, just not one this stale before now.

**Reproduced locally, deliberately, before trusting the fix**: deleted
`linkerd-demo` from the dev cluster and re-ran `kubectl apply -f
demo/k8s-linkerd` directly — reproduced the identical `namespaces
"linkerd-demo" not found` errors on a genuinely fresh namespace, not just
inferred from the CI log. Fixed `applyLinkerdDemoFixtures`
(`test/integration/linkerd_cluster.go`) to apply `namespace.yaml` alone
first, then the rest of the directory — removing the race outright rather
than relying on file-processing order (alphabetical sorting doesn't even
help here: `cascadepolicy.yaml`/`checkout.yaml` both sort before
`namespace.yaml`). Confirmed the fix against the same freshly-deleted
namespace: the two-step apply succeeded cleanly, and the full
`make test-integration` (all six tests, both meshes) passed end-to-end
from that genuinely fresh state.

## Follow-ups / known gaps
- The resource-exhaustion risk flagged above (Istio + Linkerd's full
  stacks together on a standard GitHub Actions runner) is still real and
  still unconfirmed either way — the first run failed before reaching
  that concern at all. If a later run times out during a `rollout status`
  wait rather than failing fast like this one did, the fix is likely
  trimming `linkerd viz install`'s footprint (e.g., a `--set` flag
  disabling `tap`/`tap-injector`/`web`, none of which
  `internal/mesh/linkerd`'s `QueryBuilder` reads) rather than further
  bumping the timeout.

# Phase 6.6 (slice 4): `hack/install-linkerd.sh`, live-verified

**Date:** 2026-09-01
**Author:** Claude (solo — Cursor unavailable)
**Type:** feature (new dev-environment script; no Go source changed)

## What
- `hack/install-linkerd.sh` (new): installs a pinned Linkerd control plane +
  linkerd-viz (for its bundled Prometheus) onto the current kubectl
  context, mirroring `hack/install-istio.sh`'s exact shape and
  conventions (`need`, pinned-binary-in-`bin/` download, kube-context
  sanity check, `rollout status` waits).
- `make linkerd-install` (new Makefile target under `##@ Local mesh`,
  alongside `istio-install`) + `LINKERD`/`LINKERD_VERSION` tool variables,
  same pattern as `ISTIOCTL`/`ISTIO_VERSION`.

## Why
Every live check across all three prior Phase 6.6 slices
(`QueryBuilder`, `Mitigator`, reconciler dispatch) installed Linkerd by
hand, one command at a time. This script is that same sequence, scripted
and pinned — the last piece needed before integration test coverage can
exist, since a CI job needs a repeatable install, not a transcript.

## How

### Every step mirrors what this session already live-verified, in the same order
- Gateway API CRDs installed first (Linkerd 2.16+ requires them to exist
  before `linkerd install` will proceed at all — confirmed live in the
  `QueryBuilder` slice's own spike).
- `linkerd install --crds`/`install`/`viz install` output is captured via
  stdout *only*, never `2>&1` — redirecting stderr into the same stream
  interleaves the CLI's human-readable progress text into the YAML
  document stream, confirmed live to produce `error converting YAML to
  JSON` failures at seemingly-arbitrary line numbers (the same root cause
  already documented in the `QueryBuilder` slice's worklog).
- `linkerd` CLI downloaded directly from GitHub releases
  (`linkerd2-cli-{version}-{os}-{arch}`, a raw binary, no tar.gz — a
  simpler download than `istioctl`'s own tarball), pinned to
  `edge-26.6.3` (the exact build this session's own spike ran against —
  Linkerd has no numbered stable release series the way Istio does, only
  rolling "edge" builds, so this is a specific known-good build, not a
  moving target).
- Waits only on the linkerd-viz component `internal/mesh/linkerd`'s
  `QueryBuilder` actually depends on (`prometheus`) — not `metrics-api`/
  `tap`/`web`, which are only used by the `linkerd`/`linkerd-viz` CLI's own
  dashboard commands and, per this session's own earlier live finding, can
  crash-loop under a resource-starved dev cluster without affecting
  detection at all.

### A real bug caught by live-running the script, not assumed away
The first live run failed immediately:
```
Can't install the Linkerd control plane in the 'linkerd' namespace.
Reason: ConfigMap/linkerd-config already exists.
Run the command `linkerd upgrade`, if you are looking to upgrade Linkerd.
```
Unlike `istioctl install` (`hack/install-istio.sh`'s single `install`
call, which reconciles an existing installation in place), `linkerd
install`/`install --crds` refuse outright when a control plane already
exists — a real difference between the two CLIs' philosophies, not
something the original script draft accounted for. Since this dev
cluster already had a Linkerd control plane from earlier ad-hoc work this
session, this was hit immediately, not a hypothetical edge case.

Fixed by detecting an existing install (`kubectl get configmap
linkerd-config -n linkerd`) and using `linkerd upgrade`/`upgrade --crds`
instead — the CLI's own suggested next step, rendering the equivalent
manifests for an already-installed control plane. Confirmed via `linkerd
upgrade --help`/`upgrade --crds --help` that both exist with the same
shape as their `install` counterparts before wiring the branch. `linkerd
viz install` needed no equivalent branch — confirmed live it succeeds
unconditionally whether or not linkerd-viz is already present (no
ConfigMap-existence guard the way core `install` has), so `kubectl
apply`'s own idempotency is sufficient there.

Also removed from an earlier draft: a `python3 -c "import yaml; ..."`
validation step after each render, originally used interactively during
the `QueryBuilder` slice's own spike to confirm the stdout-only-capture
fix produced clean YAML. Kept out of the committed script deliberately —
it depends on PyYAML, a third-party package not guaranteed present on
every machine or CI runner (unlike the Python standard library), and
`kubectl apply` already surfaces any real YAML problem on its own with a
clear error. A one-off interactive debugging aid isn't a good default for
a script meant to run unattended in CI.

## Live verification
Ran the script twice against the real dev cluster (which had also, by
this point, drifted into some general resource pressure over the
session's cumulative multi-day uptime — even `kube-apiserver`/
`kube-scheduler` were intermittently restarting):
1. **First run**: failed with the install-vs-upgrade error above —
   the real bug this worklog documents, caught by actually running the
   script rather than assuming it would work unchanged from the
   `install`-only draft.
2. **Second run** (after the `upgrade`-detection fix): completed
   end-to-end, correctly detecting the existing install and using
   `linkerd upgrade`/`viz install`, and both `rollout status` waits
   succeeded:
   ```
   deployment "linkerd-destination" successfully rolled out
   deployment "linkerd-identity" successfully rolled out
   deployment "linkerd-proxy-injector" successfully rolled out
   ...
   deployment "prometheus" successfully rolled out
   Linkerd edge-26.6.3 + linkerd-viz ready on context kind-cascade-operator
   ```
   Final pod state confirmed genuinely healthy, not just "rollout status
   exited 0" — every component the script actually waits on came up clean:
   ```
   linkerd-destination-6cb6c58fcf-x4x59      4/4   Running   0
   linkerd-identity-7dc647f897-zdjdc         2/2   Running   (pre-existing restart count, none new)
   linkerd-proxy-injector-85df7888c8-8ngwj    2/2   Running   0
   prometheus-748fc64499-k7xh8                2/2   Running   (pre-existing restart count, none new)
   ```
   The run also had a real side effect worth noting plainly: it left the
   control plane in a *healthier* state than before it started —
   `linkerd-destination`/`linkerd-proxy-injector` had been flapping
   (`RunContainerError`/repeated liveness-probe restarts) from the
   session's accumulated resource pressure immediately before this run,
   and the `upgrade`'s fresh rollout replaced those pods cleanly.

## Follow-ups / known gaps
- Integration-test coverage (the raw-JSON wire-format discipline used for
  Istio's three signatures, under `test/integration`) is the last
  remaining piece of Phase 6.6 — this script is what a future CI job
  (mirroring `.github/workflows/integration.yml`'s `make istio-install`
  step) would call to stand up the Linkerd side of that job, though
  wiring an actual CI job is not part of this slice.
- This script was only exercised against an already-Linkerd-experienced
  cluster (the `upgrade` path); the `install` path (a genuinely fresh
  cluster, as CI's own `kind create cluster` would produce) was exercised
  earlier in the session's `QueryBuilder`-slice spike, by hand, but not
  re-confirmed by this exact script end-to-end. Both code paths exist and
  were each exercised at some point this session, just not both through
  this one script in the same run (a fresh cluster only ever takes the
  `install` branch once).

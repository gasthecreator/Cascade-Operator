# Istio 1.30.4 → 1.31.0 upgrade: Go libraries and control-plane pin together, live-verified

**Date:** 2026-09-04
**Author:** Claude (solo)
**Type:** dependency upgrade + fix

## What
Bumped `istio.io/api`/`istio.io/client-go` and the pinned Istio control-plane
version (`ISTIO_VERSION`) from 1.30.4 to 1.31.0 together, in one slice, rather
than letting Dependabot's two proposed PRs (#41/#42, Go libraries only) land
without the control plane following — this project deliberately keeps the two
in lockstep (see `docs/dev-istio.md`), so a Go-library-only bump would have
silently drifted the tested/installed control plane out of alignment with the
code's own type assumptions.

## Why
Dependabot proposed `istio.io/client-go`/`istio.io/api` → 1.31.0 stable
(#41/#42) after `.github/dependabot.yml`'s new `ignore` rule (from
`2026-09-04-dependabot-groups-and-ignore-rules.md`) started blocking only the
1.31.0 *pre-release* candidates that PR #7 had been held on earlier. With a
real stable release now available, the right move was the full upgrade, not
a partial one — checking 1.31's changelog for breaking changes first, then
live-verifying the mitigation logic against the upgraded control plane rather
than trusting `go build` alone.

## How

### Changelog research, one claim corrected
A research pass flagged `OutlierDetection.MinHealthPercent` (the Envoy
"panic mode" threshold) as having a backwards-incompatible default change in
1.31. Checked directly against the vendored Go module source rather than
trusting the summary: `~/go/pkg/mod/istio.io/api@v1.30.4-.../networking/v1alpha3/destination_rule.pb.go`
vs. the `@v1.31.0` copy — the field's default (0%, disabled) and doc comment
are byte-identical between the two versions. The claim was inaccurate;
no code change was needed here. `internal/mitigation/outlier.go`'s trip
logic never sets this field anyway (only `Consecutive_5XxErrors`,
`Interval`, `BaseEjectionTime`), so it was moot either way — confirmed by
reading the file, not assumed.

No other breaking changes surfaced for the APIs this project actually uses
(`DestinationRule`, `VirtualService` traffic policy / retry fields).

### Go module bump
```
go get istio.io/api@v1.31.0 istio.io/client-go@v1.31.0
go mod tidy
```
Clean `go build ./...`, `go vet ./...`, `go test ./... -race` afterward —
no source changes needed in `internal/mitigation` or `internal/controller`.

### Control-plane pin, four files + docs
`ISTIO_VERSION` default bumped 1.30.4 → 1.31.0 in `hack/install-istio.sh`,
`hack/deploy-istio-samples.sh`, `hack/install-grafana.sh`, and
`.github/workflows/integration.yml` (both the env var and the job's own
display name). `docs/dev-istio.md`'s intro line and uninstall command updated
to match. Deliberately left every *historical* "1.30.4" reference in
`CHANGELOG.md`/`PLAN.md` untouched — those describe what was true at the time
of past investigations, matching this project's existing worklog/changelog
practice of preserving history rather than rewriting it.

### Live upgrade of the running control plane
`hack/install-istio.sh` re-run against the live Kind cluster — `istioctl
install` reconciles istiod/gateways in place. Confirmed via `istioctl
version` showing control plane 1.31.0. The demo topology's pods
(`checkout-service`, `payments-service`, `inventory-service`) don't pick up a
new sidecar version until restarted; rolled them with `kubectl rollout
restart`, confirmed via `istioctl proxy-status` showing all three on
1.31.0 (the unrelated `httpbin`/`sleep` dev-validation pods were deliberately
left on 1.30.4 — they're not part of the live-verification path).

### Integration suite — a real bug found, not an Istio 1.31 regression
`make test-integration` failed identically across all 5 (Istio) + 1 (Linkerd)
tests during their own `kubectl apply -f demo/k8s/` (`demo/k8s-linkerd/`)
setup step:
```
The cascadepolicies "checkout-service" is invalid: metadata.resourceVersion:
Invalid value: 0: must be specified for an update
```
Root cause: both demo `CascadePolicy` objects
(`default/checkout-service`, `linkerd-demo/checkout-service`) carried a
corrupted `kubectl.kubernetes.io/last-applied-configuration` annotation —
inspecting it directly showed a *full* object dump (including
`resourceVersion`, `generation`, `uid`, `status`), not the spec-only content
`kubectl apply` is supposed to store there. This was left over from an
earlier slice in this same session (`2026-09-03-deploy-operator-fresh-run-validation.md`)
that backed these objects up via `kubectl get ... -o yaml > backup.yaml`
before `make undeploy` (which cascade-deletes CRs along with the CRD) and
restored them via `kubectl apply -f backup.yaml` — a full `-o yaml` dump
applied this way gets stored verbatim as the tracking annotation, embedded
`resourceVersion`/`generation` included. Once those cached values drifted
from the live object's real ones, `kubectl`'s three-way-merge apply logic
produced an invalid patch, rejected server-side. Not an Istio 1.31 issue at
all — this was dormant since that earlier restore and only surfaced now
because the integration suite was the first thing since then to re-apply
`demo/k8s/cascadepolicy.yaml`.

Fixed by stripping the stale annotation on both objects:
```
kubectl annotate cascadepolicy checkout-service -n default kubectl.kubernetes.io/last-applied-configuration-
kubectl annotate cascadepolicy checkout-service -n linkerd-demo kubectl.kubernetes.io/last-applied-configuration-
```
Confirmed `kubectl apply -f demo/k8s/` and `-f demo/k8s-linkerd/` both
succeed cleanly afterward (kubectl re-establishes a correct, spec-only
annotation on the next apply). A first `make test-integration` re-run hit
one unrelated, isolated `FAIL` — consistent with this cluster's
already-documented transient-flake pattern elsewhere this session — and an
immediate second full run passed clean, all 6 tests:
```
--- PASS: TestFanOutTripAndRestoreWireFormat (43.72s)
--- PASS: TestLatencyErrorCascadeTripAndRestoreWireFormat (21.92s)
--- PASS: TestLinkerdFanOutDetectOnlyNeverPatchesTheService (9.63s)
--- PASS: TestLinkerdLatencyErrorCascadeTripAndRestoreWireFormat (24.82s)
--- PASS: TestLinkerdRetryStormTripAndRestoreWireFormat (24.28s)
--- PASS: TestRetryStormTripAndRestoreWireFormat (17.05s)
ok  	github.com/gasthecreator/Cascade-Operator/test/integration	143.016s
```
This confirms the operator's mitigation logic — trip, patch wire format,
and gradual restore, on both Istio and Linkerd — genuinely still works
correctly against the real, upgraded Istio 1.31.0 control plane.

## Follow-ups / known gaps
- The corrupted-annotation bug class (a full `kubectl get -o yaml` dump
  applied via `kubectl apply -f`) is a real, general kubectl footgun — any
  future backup/restore of a live object for this project should prefer
  `kubectl replace -f` or stripping `resourceVersion`/`generation`/`status`/
  `uid` before reapplying, not `kubectl apply -f` on a full dump. Worth
  keeping in mind rather than a new abstraction to build.
- PRs #41/#42 (Dependabot's Go-library-only 1.31.0 bumps) are superseded by
  this slice and should be closed once this lands, pointing at this PR.

## Why
The last remaining piece of PLAN.md §5 Phase 6.6 — matching Istio's own
raw-JSON wire-format discipline (a typed read cannot prove a JSON Patch or
merge patch actually reached etcd the way it was intended; only a raw,
unstructured read against a real apiserver can) for Linkerd's own three
signature implementations, completing every piece of Linkerd multi-mesh
support this project set out to build.

## How

### Separate helpers, not a generalized/shared version of the Istio ones
`cluster.go`'s existing helpers (`resourceSpecJSON`, `getPolicy`,
`assertPolicyPhase`, `reconcilePolicy`, ...) all hardcode `testNamespace`
("default") and `policyName`. Rather than retrofitting every one of them
to take a namespace parameter — real, if modest, risk to code the existing
three Istio tests already depend on working exactly as-is — this slice
adds a parallel, self-contained set scoped to `linkerd-demo`
(`getLinkerdPolicy`, `assertLinkerdPolicyPhase`, `reconcileLinkerdPolicy`,
`linkerdResourceSpecJSON`, ...), reusing only what's genuinely
namespace-agnostic already (`repoRoot`, `kubectl`, `kubeContext`,
`skipIfDisabled`, `newClusterClient`, `newReconciler`). This mirrors this
whole project's own established preference (`internal/mesh/istio` vs.
`internal/mesh/linkerd`, kept as two clearly-labeled parallel
implementations rather than one generalized abstraction) rather than
introducing a new pattern for this slice alone.

### A wire-format read that had to be annotations, not spec
Istio's three signatures all patch typed CRD spec fields, so
`resourceSpecJSON`'s `.spec`-only read is enough. Linkerd's
latency/error-cascade lives entirely in `metadata.annotations` — there is
no spec field at all for failure-accrual — so this slice adds
`linkerdResourceAnnotationsJSON` alongside `linkerdResourceSpecJSON`
(used by the retry-storm test, whose `spec.retryBudget` is a real spec
field) rather than trying to force one generic reader to cover both
shapes.

### CI-safety: skip, not fail, when Linkerd isn't there
The existing `.github/workflows/integration.yml` job only runs
`make istio-install` — it has no Linkerd control plane, and updating it
to also run `make linkerd-install` is explicitly out of scope for this
slice (see Follow-ups). `verifyLinkerdClusterReady` checks for the
`serviceprofiles.linkerd.io` CRD and calls `t.Skip` (not `t.Fatal`) when
it's absent, confirmed live: `kubectl get crd doesnotexist.linkerd.io`
exits nonzero exactly the way the real absent-CRD case would, so the same
code path this check relies on was exercised, without needing to actually
uninstall Linkerd from the dev cluster to prove it.

## Live verification (real cluster, real apiserver — every assertion reads back a live object, not a fake)
Ran the new tests directly (`go test -tags=integration ./test/integration/... -run TestLinkerd -v`)
against the dev cluster (which already had a healthy Linkerd install from
the prior slice):
- **Fan-out**: confirmed the real `Service`'s annotations are
  byte-identical before and after a trip+restore cycle — only
  `kubectl.kubernetes.io/last-applied-configuration` present throughout,
  proving Linkerd's detect-only fan-out path never writes anything, not
  just that the unit tests claim so.
- **Latency/error-cascade**: confirmed the real `Service` picked up
  `balancer.linkerd.io/failure-accrual: consecutive`,
  `-consecutive-max-failures: "3"`, `-consecutive-min-penalty: "30s"` on
  trip, then lost every one of those five annotations (including the two
  operator-tracking ones) after a full six-tick restore cycle through
  `Reconcile` itself.
- **Retry storm**: confirmed the real `ServiceProfile`'s `retryBudget`
  went from the fixture's seeded `{retryRatio: 1, minRetriesPerSecond: 10,
  ttl: "10s"}` to fully suppressed `{0, 0, "10s"}` on trip, and the
  pre-existing `isRetryable` route survived untouched throughout, then
  restored to byte-identical original values after the same six-tick
  cycle.

Then ran the **full** `make test-integration` (the exact command
`.github/workflows/integration.yml` invokes) — all six tests, Istio's
three existing ones and this slice's three new ones, passed together in
one run with no cross-fixture interference (the two meshes' demo
topologies live in fully separate namespaces):

Confirmed the dev cluster's `linkerd-demo` namespace was left in a clean
state afterward: `CascadePolicy` back at `Phase: Normal`, the `Service`'s
annotations back to none, the `ServiceProfile`'s `retryBudget` back at its
seeded original.

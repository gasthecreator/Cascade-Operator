# Phase 6.6 (slice 1): Linkerd `QueryBuilder`, live-verified against a real Linkerd install

**Date:** 2026-08-31
**Author:** Claude (solo — Cursor unavailable)
**Type:** feature (new package; no existing behavior change — not yet wired into the reconciler)

## What
- `internal/mesh/linkerd/query_builder.go`: `QueryBuilder` implementing
  `mesh.QueryBuilder` for Linkerd — `LatencyP99Query`, `ErrorRateQuery`,
  `RetryStormRatioQuery`, `FanOutRatioQuery` — mirroring
  `internal/mesh/istio`'s shape exactly (stateless, pure `fmt.Sprintf`).
- `internal/mesh/linkerd/resolve.go`: small `deploymentLabel`/
  `namespaceLabel` helpers around the existing `mitigation.ParseServiceFQDN`,
  needed because Linkerd's inbound proxy metrics carry no FQDN-shaped label
  (see below).
- `demo/k8s-linkerd/{namespace,checkout,payments,inventory}.yaml`: a
  Linkerd-injected copy of the demo topology in a new `linkerd-demo`
  namespace, reusing the already-built `cascade-demo-*:dev` images — the
  live environment this slice's queries were verified against.
- No reconciler wiring yet — `CascadePolicyReconciler.queryBuilder()` still
  always defaults to `istio.QueryBuilder{}` regardless of `spec.mesh`.
  Dispatching on `policy.Spec.Mesh` is deliberately deferred to the
  `Mitigator` slice, since a `QueryBuilder`-only dispatch would let a
  `Linkerd` policy detect signatures it could never mitigate — not useful
  as an intermediate state.

## Why
PLAN.md §5 Phase 6.6 requires Linkerd's actual metric shapes "confirmed
against a real Linkerd install's actual scrape output... not assumed from
documentation alone" — the same discipline the original Istio queries were
held to (PROPOSALS.md's resolved "sum by (le)" entry). This slice is that
spike plus the `QueryBuilder` it produced, kept separate from the larger
`Mitigator`/arbitration/reconciler-wiring slice to follow, matching this
project's one-slice-per-PR pattern from 6.3/6.4/6.5.

## How — the live spike
Installed a real Linkerd 2.16 control plane + `linkerd-viz` (for its bundled
Prometheus) onto the existing dev Kind cluster, alongside the already-
running Istio install — isolated onto a brand-new `linkerd-demo` namespace
(`linkerd.io/inject: enabled`) so it never competes with the Istio-injected
`default` namespace's identically-named services. Generated real traffic
(a `curl` pod issuing repeated GETs to `checkout-service`, which calls
`payments-service`/`inventory-service`) and queried Linkerd's own Prometheus
directly for the real metric shapes, rather than assuming them from the
plan's draft text.

**Two corrections against the plan's own draft fell out immediately:**
- The request counter is `request_total`, not `response_total` — but
  `response_total` *is* a real, different metric (completed responses, with
  a `classification` label), used below for `ErrorRateQuery`.
- The latency histogram is `response_latency_ms_bucket`, not
  `route_response_latency_ms_bucket`.

**Per-query findings:**
- `LatencyP99Query`/`ErrorRateQuery`: `response_latency_ms_bucket` and
  `response_total` both carry an `authority` label that — confirmed live —
  equals the plain Service FQDN for in-cluster calls (this project's only
  supported call shape), giving an Istio-`destination_service`-equivalent
  exact-match label. `response_total` also carries `classification`
  (`"success"`/`"failure"`) and `status_code` — confirmed live via
  `demo/internal/depsvc`'s `/control/fail` handler (a real 500) producing
  `classification="failure"`.
- `RetryStormRatioQuery` needed real investigation, not a direct swap of
  labels: Linkerd has no `reporter=source`/`reporter=destination` split.
  Applying a `ServiceProfile` retry budget to `inventory-service` and
  driving failing traffic through it while comparing `request_total`
  `direction=outbound` (at the caller) against `direction=inbound` (at the
  dependency) showed both **already amplified equally** (160 vs. 161 in one
  live run) — because the same caller proxy that is being measured is also
  the one performing the retries, so its own outbound count already
  includes every attempt. Neither side gives a "logical calls" baseline.
  Digging into Prometheus's own metric name list surfaced a
  ServiceProfile-route-scoped pair built for exactly this:
  `route_request_total` (one row per original application-level call) and
  `route_actual_request_total` (one row per physical attempt, retries
  included) — confirmed live at a 130:30 ratio (~4.3x) for the same failing
  traffic, the real Linkerd equivalent of Istio's reporter split. This pair
  only exists once a `ServiceProfile` exists for the dependency — an
  acceptable precondition, since retry storm's own Linkerd mitigation
  (next slice) is that same `ServiceProfile`'s `retryBudget`, exactly
  mirroring Istio's retry-storm signature already assuming a pre-existing
  `VirtualService` retry policy (`demo/k8s/inventory-retry-vs.yaml`).
- `FanOutRatioQuery`: confirmed live that `direction=inbound` samples carry
  no FQDN-shaped label at all (no `authority`, no `dst_service` — those only
  exist on the `outbound` side, where the proxy knows what it's calling).
  Since there is no "outbound-toward-the-caller" view either (nothing
  meshed calls into `checkout-service` from outside the mesh in this
  topology), both sides resolve the host to a `deployment`/`namespace`
  label pair via `mitigation.ParseServiceFQDN` — assumes Service and
  Deployment share a name, true for every manifest in `demo/k8s` and
  `demo/k8s-linkerd`, the same convention the Istio migration already
  relies on. `authz_name!="probe"` excludes kubelet liveness/readiness
  traffic (confirmed live on the proxy's admin port) without hardcoding a
  container port.

Every query string in `query_builder_test.go`'s `want` values is the exact
string run live against the dev Prometheus (`kubectl -n linkerd-viz
port-forward svc/prometheus`) during this spike, not retyped from memory.

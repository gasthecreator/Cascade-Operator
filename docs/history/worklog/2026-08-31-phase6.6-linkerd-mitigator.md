# Phase 6.6 (slice 2): Linkerd `Mitigator`, live-verified against the real cluster

**Date:** 2026-08-31
**Author:** Claude (solo — Cursor unavailable)
**Type:** feature (new package; no existing behavior change — not yet wired into the reconciler)

## What
- `internal/mesh/linkerd.Mitigator` implementing `mesh.Mitigator` for
  Linkerd's three signatures:
  - **Latency/error-cascade** → `balancer.linkerd.io/failure-accrual*`
    Service annotations (`failureaccrual.go`).
  - **Retry storm** → `ServiceProfile.spec.retryBudget`
    (`retrybudget.go`), patched via a new hand-written, minimal typed
    client for Linkerd's ServiceProfile CRD
    (`internal/mesh/linkerd/serviceprofile/v1alpha2`).
  - **Fan-out amplification** → detect-only (Linkerd has no connection-
    pool/concurrency-limiting equivalent): `ApplyTrip` still resolves the
    dependency's Service so `DependencyObjectMissing` stays meaningful,
    but never patches anything, in either `PolicyMode`, and says so
    explicitly in its log line every call.
- `internal/mesh/linkerd/ramp.go`: the shared 5-step restore-ramp math
  (mirrors `internal/mitigation`'s own `restoreProgress`, duplicated
  rather than exported since that function is unexported and this is a
  different mesh package).
- `internal/mesh/linkerd/mitigator_test.go`: direct unit tests against a
  fake `controller-runtime` client (not routed through `Reconcile` —
  reconciler `spec.mesh` dispatch isn't wired yet, see Follow-ups) —
  missing-object, `DetectOnly` no-op, first-trip capture, and full
  restore-ramp-to-completion for both patched signatures, plus fan-out's
  always-`false` `HasManagedEdges`.
- `cmd/main.go`: registers the new ServiceProfile scheme
  (`spv1alpha2.AddToScheme`) and the new `Service`/`serviceprofiles` RBAC
  markers, regenerated into `config/rbac/role.yaml` via `make manifests`.

## Why
PLAN.md §5 Phase 6.6 calls for Linkerd's actual `Mitigator` implementation,
the failure-accrual/ServiceProfile arbitration this mesh's own
incompatibility forces, and — per this project's whole-session discipline
— confirmed live, not assumed from documentation. This is that build, kept
as its own slice after `QueryBuilder` (the prior slice), matching the
one-slice-per-PR pattern from the Istio migration's own 6.3/6.4/6.5.

## How

### Retry-storm trip direction, corrected against the plan's own draft intuition
Re-reading `internal/mitigation/retries.go` before writing this Mitigator
surfaced that Istio's retry-storm trip **cuts** `retries.attempts` to 0
(suppressing retries, not enabling them) — the storm is retries hammering
a failing dependency, so mitigation stops them, then ramps back up toward
the true original once healthy. The Linkerd equivalent trips
`retryBudget.retryRatio`/`minRetriesPerSecond` to `(0, 0)`, fully
suppressing retries regardless of the pre-existing budget's own ratio or
floor, then ramps both back toward the captured original across the same
five-step ramp every other signature uses.

### A hand-written, minimal ServiceProfile client — not the upstream `linkerd2` module
`github.com/linkerd/linkerd2`'s generated clientset is Linkerd's entire
control-plane monorepo, with its own large, independent dependency graph —
a heavy, version-fragile addition for one CRD type, next to this project's
already-pinned `istio.io/client-go` (a purpose-built, narrowly-scoped
client library, not a monorepo). `internal/mesh/linkerd/serviceprofile/v1alpha2`
is instead a small, hand-written subset (only `spec.routes[]`,
`spec.retryBudget` — `dstOverrides`/`responseClasses`/`opaquePorts` are
omitted, out of scope for every signature this Mitigator implements),
following the exact same `SchemeBuilder`/`AddToScheme`/
`+kubebuilder:object:generate=true` shape controller-gen already produces
for `api/v1alpha1` — an ordinary extension of tooling this project already
depends on, not a new one. Every field name and requiredness was confirmed
directly against the live cluster's installed CRD
(`kubectl get crd serviceprofiles.linkerd.io -o json`, both the `v1alpha1`
and `v1alpha2` served versions — `v1alpha2` is the storage version and
what this package targets), including the concrete finding that
`retryRatio`/`minRetriesPerSecond` carry no CRD-level minimum, so a
trip-time value of exactly 0 is schema-legal (confirmed by applying it
directly, see "Live verification" below) — this struct's fields also
deliberately omit `omitempty` on those two, so a typed `client.Update()`
survives the exact-zero write without the zero-value-vs-omitempty problem
this project's *vendored* Istio proto types needed hand-built JSON Patch
bytes to work around; this struct is hand-written for exactly this
Mitigator, so the tags simply don't need that workaround.

**A real mistake caught and fixed before it shipped**: the first version of
this new package marked `ServiceProfile`/`ServiceProfileList` with
`+kubebuilder:object:root=true` (the standard kubebuilder-scaffolded
shape) on the assumption that marker was what gates `make manifests`'
`crd` generator into treating a type as a CRD-root candidate. Running
`make manifests` immediately produced a real, generated
`config/crd/bases/linkerd.io_serviceprofiles.yaml` — this project's own
copy of a schema it does not own, which `make install` would then try to
install over or alongside Linkerd's own already-installed CRD. Removing
that marker (and, on a second wrong guess, the `+groupName` marker too)
did **not** stop the generation — confirmed by reading
`controller-tools@v0.21.0`'s own `pkg/crd/parser.go` directly: `crd`
generation is gated by a *different*, package-level `+kubebuilder:skip`
marker checked in `indexTypes` before any type in the package is even
considered, independent of `object:root`/`object:generate`. Fixed by
adding that marker to `groupversion_info.go`'s package doc comment
(confirmed: `make manifests` now produces zero files under
`internal/mesh/linkerd/serviceprofile/`, and `DeepCopyObject` — which
`object:root` would otherwise have generated — is instead hand-written in
`deepcopy_object.go`, three lines each, since `DeepCopyInto`/`DeepCopy`
still come from `make generate` via `object:generate=true` alone).

### The "arbitration" PLAN.md called for is mostly already-existing machinery, not new code
Linkerd's own docs (fetched during the `QueryBuilder` slice, restated in
`mesh.go`'s doc comment) state circuit breaking is ignored for as long as
*any* `ServiceProfile` exists for a Service, regardless of that
ServiceProfile's own field values. Re-reading
`internal/controller/restore.go`'s `forceCompleteOutgoingRestore` before
building new bookkeeping for this found it is **already fully
mesh-agnostic** — it drives entirely through `mesh.Mitigator`'s own
`HasManagedEdges`/`CompleteRestore`, keyed on `status.LastSignature`
(one `CascadePolicy` tracks exactly one active signature at a time). So
the same-policy handoff between latency/error-cascade and retry storm on
Linkerd needed no new arbitration code at all — only correctly
implementing `HasManagedEdges`/`CompleteRestore` for each signature below
`mesh.Mitigator`, exactly as already required for every other signature.

What *isn't* solved by that — stated plainly rather than glossed over,
matching this project's own "verify, don't assume, state the caveat"
practice for every other mesh-specific limitation this session has hit:
a dependency that has a pre-provisioned `ServiceProfile` (needed for retry
storm's own mitigation to have something to patch — this Mitigator only
ever patches an existing object, never creates or deletes one, the same
convention as every other signature/mesh in this project) can **never**
also receive latency/error-cascade's failure-accrual mitigation on this
mesh, even immediately after `CompleteRestore` has reset that
ServiceProfile's `retryBudget` back to its true original — the *object's
mere existence* is what Linkerd's own proxy uses to suppress circuit
breaking, not its current field values, and deleting the ServiceProfile
object to work around that would break this project's own "never own
object lifecycle" convention. `applyLatencyErrorTrip` detects this (a
best-effort `Get` for a ServiceProfile at the same host) and logs it,
purely informationally — it still applies the annotations regardless,
since the operator can't know from here whether Linkerd will end up
honoring them, and doing nothing would be a silent, confusing gap. See
`mitigator.go`'s own package doc comment for the full writeup.

### Fan-out stays honestly detect-only
`ApplyTrip`'s fan-out path resolves the dependency's Service (so a missing
dependency still surfaces `DependencyObjectMissing` the same as every
other signature) but never patches anything in either `PolicyMode`, with
an explicit Info-level log line every call stating there is no Linkerd
primitive for this signature. `HasManagedEdges` always returns `false` for
this signature, so `internal/controller`'s existing, unmodified
`beginRestoreFanOut`/`advanceRestoreFanOut` snap straight back to `Normal`
without ever calling `ApplyRestoreStep`/`CompleteRestore` — no
Linkerd-specific controller code needed for this to behave correctly.

## Live verification (real cluster, real typed client — not only the fake-client unit tests)
Built a small throwaway program (`cmd/_live_verify_tmp`, deleted after use
— not committed) constructing this `Mitigator` around a real
`controller-runtime` client against the dev Kind cluster's live Linkerd
install, and ran the full trip → inspect → restore cycle for both patched
signatures:
- **Retry storm** against a real `ServiceProfile` seeded with
  `{retryRatio: 1.0, minRetriesPerSecond: 10, ttl: 10s}`: `ApplyTrip`
  produced the real object's `retryBudget` as
  `{RetryRatio:0 MinRetriesPerSecond:0 TTL:10s}` (confirmed: the live API
  server accepts the exact zero-value trip payload — no CRD-schema
  minimum rejected it), left `spec.routes` untouched, and captured
  `{"retryRatio":1,"minRetriesPerSecond":10,"ttl":"10s"}` as the original.
  `HasManagedEdges` returned `true`. `CompleteRestore` wrote the real
  object's `retryBudget` back to exactly `{RetryRatio:1
  MinRetriesPerSecond:10 TTL:10s}` and stripped both operator annotations.
- **Latency/error-cascade** against a real `Service` with no prior
  failure-accrual annotations: `ApplyTrip` produced the real object's
  annotations as `failure-accrual=consecutive`,
  `failure-accrual-consecutive-max-failures=3`,
  `failure-accrual-consecutive-min-penalty=30s`, `managed-by=cascade-operator`,
  and `original-failure-accrual={"unset":true}`. `CompleteRestore` removed
  every one of those five annotations, leaving the Service exactly as it
  started (only `kubectl.kubernetes.io/last-applied-configuration`
  remained, untouched throughout since it isn't a key this Mitigator
  reads or writes).
